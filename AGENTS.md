# AGENTS.md
## Постоянные правила проекта TOPGUN · Мой день

Перед любой существенной работой обязательно прочитай `PRODUCT_SPEC.md`.

## Главный принцип

Этот проект — локальный MVP для понятного персонального разбора результатов барбера по XLSX/CSV.

Не расширяй задачу в полноценную CRM, SaaS или корпоративную платформу без прямого запроса.

## Работа с файлами

- Работай преимущественно внутри текущей папки проекта.
- Не удаляй исходные файлы из `data/` и `references/`.
- Результаты экспорта приложения сохраняй отдельно.
- Не перезаписывай пользовательские файлы молча.
- Поддерживай кириллицу и пробелы в путях.

## Данные

- Не выдумывай отсутствующие поля.
- Не подставляй случайные значения вместо отсутствующих данных.
- Если обязательного поля нет, покажи понятное сообщение.
- Если данных недостаточно для сравнения, так и сообщи.
- Не требуй ФИО, телефоны или email клиентов для работы MVP.
- Не отправляй данные во внешние сервисы.

## Расчёты

- Все KPI рассчитывай детерминированным кодом.
- Формулы должны соответствовать `PRODUCT_SPEC.md`.
- Бизнес-пороги должны храниться централизованно и быть легко изменяемыми.
- Не используй LLM для арифметики.
- Не скрывай методику расчёта.
- Добавь проверку ключевых расчётов на демо-данных.

## Аналитика сотрудника

- Оценивай показатели, а не личность человека.
- Не делай выводов о мотивации, характере, потенциале или профессиональной пригодности.
- Не создавай кадровые рекомендации.
- Не создавай рейтинг «лучший / худший».
- Основной ориентир — собственная динамика сотрудника.
- Второй ориентир — среднее команды за сопоставимый период.

## Рекомендации

- В v0.1 рекомендации формируются прозрачными правилами.
- Не добавляй внешние LLM/API без прямого запроса.
- Отделяй факт от рекомендации.
- Не выдумывай проблемы, если показатели стабильны.

## Интерфейс

- Основной язык — русский.
- Используй `references/TOPGUN_MyDay_prototype_v01.html` как визуальный и композиционный референс.
- Интерфейс должен быть понятен человеку без навыков программирования.
- Используй пользовательские названия: «Средний чек», «Следующая запись», «Фокус на следующий день».
- Не засоряй основной экран техническими терминами.
- Ошибки объясняй простым языком.

## Изменения проекта

Перед крупным изменением:

1. коротко объясни цель;
2. перечисли файлы, которые изменишь;
3. назови возможные риски;
4. только после этого вноси изменения.

После изменения:

1. запусти тесты;
2. запусти приложение;
3. проверь базовый сценарий на `data/demo_topgun.xlsx`;
4. сообщи, что именно проверено;
5. перечисли оставшиеся ограничения.

## Техническая простота

Предпочитай минимально достаточную архитектуру.

Не добавляй:
- сервер;
- базу данных;
- Docker;
- Redis;
- облачную инфраструктуру;
- микросервисы;
- сложный фронтенд-фреймворк;

если это не требуется для Definition of Done.

Если хочешь добавить новую зависимость или существенно изменить стек, сначала объясни необходимость.

## Scope

Источником истины по функциональности является `PRODUCT_SPEC.md`.

Если запрос пользователя противоречит ему:
- укажи противоречие;
- предложи минимальный вариант;
- не меняй бизнес-логику молча.
