# TOPGUN · Мой день
## PRODUCT_SPEC.md

Версия: v0.2  
Статус: контракт демонстрационного рабочего прототипа для совместной настройки аналитики с Никитой

## 1. Назначение продукта

`TOPGUN · Мой день v0.2` — локальное Windows-приложение, которое превращает XLSX/CSV с обезличенными данными о визитах в понятный персональный отчёт выбранного мастера.

Цель v0.2 — не построить законченную аналитическую платформу, а подготовить рабочий прототип для встречи с Никитой. Прототип должен:

- показать структуру будущего отчёта на синтетических данных;
- детерминированно рассчитать доступные показатели;
- сравнить мастера с самим собой;
- явно показать неподтверждённые определения как DATA GAP;
- позволить формализовать, проверить и активировать первое подтверждённое бизнес-правило без изменения Python-кода.

Приложение оценивает показатели, а не личность сотрудника. Оно не делает кадровых выводов и не определяет самостоятельно, что является хорошим или плохим результатом.

## 2. Источники истины

Назначение рабочих документов разделено строго:

- `PRODUCT_SPEC.md` описывает продуктовый и технический контракт приложения;
- `METRICS_MAP.md` описывает рабочую карту показателей;
- `DATA_GAPS.md` фиксирует неподтверждённые поля, формулы и определения;
- `BUSINESS_RULES.md` хранит человекочитаемое описание экспертной логики;
- `config/business_rules.json` является единственным исполняемым источником формализованных бизнес-правил.

Текст из `BUSINESS_RULES.md` не исполняется приложением. Правило может влиять на отчёт только после переноса в JSON-конфигурацию и получения статуса `ACTIVE`.

## 3. Границы v0.2

Прототип остаётся локальным и минимальным. В него не входят:

- сервер, база данных, Docker и облачная инфраструктура;
- CRM-интеграция;
- внешние LLM/API;
- авторизация и личные кабинеты;
- рейтинги мастеров и кадровые рекомендации;
- автоматически придуманные нормативы;
- прогнозирование;
- полноценный редактор бизнес-правил в интерфейсе;
- автоматическое сопоставление похожих названий полей с реальной выгрузкой «Заботы».

Стабильный архив v0.1 и существующий `data/demo_topgun.xlsx` не изменяются. Рабочая версия приложения развивается до v0.2 с сохранением совместимости с демонстрационным форматом v0.1 там, где это возможно без выдумывания данных.

## 4. Данные для демонстрации

Для v0.2 используется отдельный файл:

`data/demo_topgun_v02.xlsx`

Он должен быть явно обозначен как `SYNTHETIC DEMO DATA`. Его структура и формулы существуют только для демонстрации прототипа и не считаются реальной структурой или подтверждённой методикой «Заботы».

Минимальный демонстрационный набор содержит:

- `date` — дата визита;
- `barber` — синтетический мастер;
- `visit_id` — уникальный идентификатор визита;
- `client_id` — обезличенный синтетический идентификатор клиента;
- `branch` — синтетический филиал;
- `service_revenue` — выручка от услуг за визит;
- `product_revenue` — продажи товаров за визит;
- `has_extra_service` — наличие дополнительной услуги: `Да/Нет`;
- `prebooked` — наличие предварительной записи: `Да/Нет`.

В synthetic demo одна строка соответствует одному визиту. Для реальной выгрузки уровень строки остаётся DATA GAP до подтверждения.

## 5. Выбор периода

Anchor date набора данных — максимальная корректная дата в загруженном наборе.

Для выбранного периода длиной `N` календарных дней:

- текущий период заканчивается anchor date и включает `N` календарных дней;
- предыдущий сопоставимый период содержит непосредственно предшествующие `N` календарных дней;
- текущий и предыдущий периоды не пересекаются.

Пример для anchor date 09.08.2026 и периода 7 дней:

- текущий период: 03.08.2026–09.08.2026;
- предыдущий период: 27.07.2026–02.08.2026.

Основное сравнение v0.2 — мастер с самим собой. Командное среднее не считается нормативом и не участвует в активной интерпретации.

## 6. Единый слой расчёта метрик

`topgun_myday/metrics.py` является единственным местом детерминированного расчёта всех производных показателей отчёта, включая:

- `visits_count`;
- `revenue_total`;
- `average_check`;
- `extra_service_visit_share`;
- `product_sales`;
- `prebooking_rate`;
- другие производные показатели, которые будут подтверждены позднее.

Модули загрузки, интерфейса, HTML-экспорта и бизнес-правил не дублируют арифметические формулы.

Единый результат метрики поддерживает как минимум:

- `metric_id` — стабильный идентификатор;
- `status` — состояние доступности;
- `value` — рассчитанное значение или `null`;
- `unit` — единица измерения;
- `numerator` — числитель или исходная абсолютная величина;
- `denominator` — знаменатель, если применим;
- `reason` — понятное объяснение недоступности или ограничения.

Допустимые статусы:

- `AVAILABLE` — метрика рассчитана по доступным и определённым данным;
- `DATA_GAP` — поле или формула не подтверждены;
- `INSUFFICIENT_DATA` — определение известно, но данных выбранного периода недостаточно.

Нулевой знаменатель не приводит к делению на ноль. Результат получает статус `INSUFFICIENT_DATA` и понятную причину.

## 7. Формулы synthetic demo

Формулы этого раздела применяются только к явно обозначенному synthetic demo:

`visits_count = count(distinct visit_id)`

`revenue_total = sum(service_revenue + product_revenue)`

`average_check = revenue_total / visits_count`

`extra_service_visit_share = visits(has_extra_service = Да) / visits_count`

`product_sales = sum(product_revenue)`

`prebooking_rate = visits(prebooked = Да) / visits_count`

Эти формулы не подтверждают методику реальной аналитики TOPGUN. До согласования реальной карты полей и формул соответствующие вопросы остаются в `DATA_GAPS.md`.

## 8. Отображение динамики

Для денежных и других абсолютных показателей отчёт показывает:

- текущее значение;
- значение предыдущего сопоставимого периода;
- абсолютное изменение;
- относительное изменение, если предыдущее значение не равно нулю.

Для долей отчёт показывает:

- текущее значение;
- значение предыдущего сопоставимого периода;
- изменение только в процентных пунктах.

Для долей не выводится относительное процентное изменение. Если сравнение невозможно, отчёт показывает причину вместо придуманной дельты.

## 9. Структура отчёта

Отчёт v0.2 содержит:

1. Шапку: мастер, категория при наличии, филиал, период, источник и тип данных.
2. Четыре KPI: средний чек, доля визитов с допуслугой, продажи товаров, предварительная запись.
3. «Твоя динамика»: сравнение с непосредственно предыдущим периодом той же длины.
4. Контекст периода: визиты, уникальные клиенты и общая выручка; другие показатели — только при подтверждённых данных.
5. «Ориентир».
6. «Что изменилось»: нейтральные факты.
7. «Зона внимания»: результат только подтверждённых активных правил.
8. «Фокус»: результат только подтверждённых активных правил.
9. Источник, методику и ограничения.

Недоступная карточка не получает случайное значение. Она показывает статус и понятную причину.

## 10. Ориентир

В v0.2 слой ориентира намеренно минимален:

`status = NOT_CONFIGURED`

Интерфейс и HTML-отчёт показывают:

«Ориентир не настроен. База сравнения должна быть подтверждена.»

Приложение не подставляет автоматически среднее команды, филиал, категорию или исторический диапазон вместо неподтверждённого ориентира.

## 11. Нейтральная интерпретация

До появления правил со статусом `ACTIVE` разрешены только фактические формулировки:

- показатель вырос или снизился;
- значение изменилось на N рублей;
- относительное изменение составило N процентов;
- доля изменилась на N процентных пунктов;
- данных недостаточно;
- формула или поле ещё не подтверждены.

Без `ACTIVE`-правила запрещены:

- оценки «хорошо», «плохо», «норма», «отстаёт»;
- пороги 5% и 10% из v0.1;
- позитивная или негативная интерпретация цвета;
- автоматически выбранная сильная сторона;
- автоматически придуманная зона внимания;
- существующие автоматические рекомендации v0.1;
- причинные и кадровые выводы.

При пустой исполняемой конфигурации:

- «Зона внимания»: «Бизнес-логика для определения зоны внимания пока не настроена.»;
- «Фокус»: «Фокус появится после подтверждения бизнес-правил.»

## 12. Исполняемые бизнес-правила

`config/business_rules.json` — единственный исполняемый источник правил. На старте v0.2 он имеет версию схемы и пустой список `rules`, поэтому активных правил нет.

Движок должен:

- валидировать структуру конфигурации;
- игнорировать `DRAFT`, `NEEDS_DATA`, `NEEDS_CONFIRMATION` и `RETIRED`;
- исполнять только `ACTIVE`;
- не исполнять правило, если нужная метрика недоступна;
- возвращать понятную причину неприменимости;
- проверять примеры правила тем же вычислительным путём, который используется в отчёте.

Поддержка первого простого правила должна включать условия над рассчитанными метриками, контекстом и собственной динамикой, а также минимум три примера: срабатывание, несрабатывание и пограничный случай.

## 13. Интерфейс и экспорт

Основной язык — русский. Визуальная основа v0.1 сохраняется: тёмный современный интерфейс, крупные KPI, высокая читаемость и янтарный акцент.

Synthetic demo должен иметь заметную маркировку `SYNTHETIC DEMO DATA` в интерфейсе и HTML-отчёте.

Экспорт остаётся автономным HTML:

- без сети и внешних ресурсов;
- без `client_id` и построчных клиентских данных;
- с подтверждением перезаписи;
- с формулами, статусами доступности и источником данных;
- пригодным для печати в PDF средствами браузера.

## 14. Acceptance criteria v0.2

Прототип считается принятым, если:

1. Стабильный архив v0.1 и `data/demo_topgun.xlsx` не изменены.
2. Новый synthetic demo явно помечен и не выдаётся за формат «Заботы».
3. Все производные показатели рассчитываются только через `metrics.py`.
4. Четыре KPI synthetic demo совпадают с контрольными ручными расчётами.
5. Периоды определяются от максимальной даты и не пересекаются.
6. Денежные и абсолютные показатели показывают абсолютную и относительную дельту.
7. Доли показывают изменение только в процентных пунктах.
8. DATA GAP и недостаток данных различаются статусами и понятными причинами.
9. Главное сравнение — мастер с самим собой; командная оценка отсутствует.
10. Ориентир имеет статус `NOT_CONFIGURED` и утверждённый текст.
11. При отсутствии `ACTIVE`-правил отчёт содержит только нейтральные факты.
12. Пороги, оценки и рекомендации v0.1 не участвуют в активной логике v0.2.
13. HTML не содержит клиентских строк и не перезаписывается молча.
14. Все автоматические тесты и GUI-smoke проходят.
15. Пройден end-to-end сценарий первого правила без изменения Python-кода:
    - правило добавлено в JSON неактивным;
    - три примера проверены тем же движком;
    - после подтверждения статус изменён на `ACTIVE`;
    - приложение перезапущено;
    - правило корректно влияет на «Зону внимания» и «Фокус»;
    - Python-код между добавлением и активацией правила не изменялся.

## 15. DATA GAP как часть продукта

DATA GAP не считается ошибкой прототипа. Это явное состояние неподтверждённого контракта, предназначенное для совместной работы с Никитой.

Если реальная выгрузка не позволяет надёжно определить поле или формулу, приложение не угадывает соответствие. Вопрос фиксируется в `DATA_GAPS.md`, а зависимая метрика получает статус `DATA_GAP` до подтверждения.
